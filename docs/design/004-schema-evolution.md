# 004 — Schema evolution

**Status:** Accepted.
**Related:** [`../ARCHITECTURE.md`](../ARCHITECTURE.md), [`002-container-base.md`](002-container-base.md).

## Context

Three JSON schemas are the boundaries between subsystems (`ARCHITECTURE.md` → System boundaries):

- `snapshot-input-schema.json` — producer → snapshot analyser
- `snapshot-output-schema.json` — snapshot → live analyser
- `live-output-schema.json` — live analyser → external observability

Once a downstream depends on a schema, changing it silently breaks them. Need explicit evolution rules before any consumer is wired.

## Decision

**Semver on each schema. Additive-only within a major. Breaking changes require a major bump + parallel emit window.**

### Rules

1. **Every schema has a `schema_version: "MAJOR.MINOR"` field.** Required at the top of every emitted document. Consumers refuse unknown majors, log-warn on unknown minors.
2. **Additive within a major** — new optional fields OK. Never rename, never remove, never change type, never tighten enum, never make optional → required.
3. **Breaking change** = major bump. New file path suffix: `snapshot-output-schema-v2.json`. Old schema stays valid.
4. **Dual-emit window** — during a breaking migration, producers emit **both** v1 and v2 side-by-side to different S3 prefixes (`output/v1/result.json` + `output/v2/result.json`) until all consumers switch. Producer PR that starts the migration lists the deadline in the PR body.
5. **Schema files live in `shared/schemas/`** — one file per (schema, major-version). Pydantic models in `shared/mmc_shared/schemas/` mirror them, generated by `datamodel-code-generator` on CI.
6. **`extra: forbid`** on every Pydantic model. Unknown fields fail validation at container startup — no silent drift.
7. **CI check** — schema files under `shared/schemas/` are immutable once merged. Modifying an existing file fails CI; only new files may be added.

### Version negotiation

- Producer writes `schema_version` into every output.
- Consumer at startup: parse major → refuse if unknown → log if minor unknown.
- No runtime negotiation, no capability discovery. Deploys are coordinated by the human, not the code.

## Rationale

- SemVer + additive-only is the least surprising rule for JSON contracts (JSON Schema, OpenAPI, Kafka Avro all converge here).
- Dual-emit costs one S3 prefix — cheaper than a coordinated big-bang deploy.
- Immutable schema files in git make the "when did v1 change?" question trivial.

## Alternatives rejected

- **No versioning — always latest.** Downstream breaks the day a producer adds a field with default. Been there.
- **Runtime capability negotiation.** Overengineered for a 3-subsystem, 1-team project. Deploy-time coordination is enough.
- **Protobuf / Avro.** Better tooling for evolution, but adds a schema-registry service to run and code-gen to every container. YAGNI unless we hit a real evolution pain first.

## Consequences

- Every schema change is a deliberate PR — you name the version, you write the migration note.
- `shared/schemas/` grows monotonically. That's fine; old files are cheap.
- Consumers must gracefully handle unknown minor (log-warn + accept), or unknown major (refuse). Base image (`002`) enforces this at startup.
- Breaking migrations cost one dual-emit window each. Cost is bounded.
